### Запуск

Для того, чтобы запустить проект, у вас должен быть установлен и запущен `Docker`, а также обязательно пакетный менеджер `uv` (если его у вас нет, то вам сюда - [гайд по установке](https://docs.astral.sh/uv/getting-started/installation/)).

Первым делом поднимите `Docker`-контейнер проекта:

```bash
  docker compose up -d
```

Потом обязательно распакуйте веса:

```bash
  uzip finetuned_rubert.zip -d finetuned_rubert
```

Соберите Python-окружение:

```bash
  uv sync
```

Для того, чтобы запустить код выполните:

```bash
  uv run avito-data-science-bootcamp-2026
```

В папке data/ должны лежать train.parquet, benchmark_queries.parquet, benchmark_items.parquet. При первом запуске пересобираются кэши (data/items_parsed.parquet, data/item_embeddings.npy) и индексы ES/Qdrant — это долго (~10 минут), при последующих запусках используются кэши. Если меняется формат текста для эмбеддингов — кэши нужно удалить вручную.

### Общая идея решения

Благодаря бэкграунду в поиске я сразу выбрал гибридную схему ретривала, которая оказалась верным фундаментом:

1. Elasticsearch (BM25) — полнотекстовый поиск;
2. Qdrant (dense) — семантический поиск по эмбеддингам;
3. RRF — объединение двух ранжированных списков в один.

Модель энкодера — cointegrated/rubert-tiny2: инференс должен работать на ноутбуке, а дообучение доступно в Colab/Kaggle. Для улучшения dense-поиска энкодер дообучен контрастивно (MNRL) на парах «запрос → кликнутое объявление» из train.parquet. Модель сходится быстро — заметный прирост качества наблюдается уже после первых эпох.

**Протокол оценки**. Все замеры внутри проекта делались на фиксированной eval-выборке: 2000 уникальных запросов (seed=42), тексты которых исключены из обучения энкодера. На eval-выборке Recall@50 = 0.84; итог на скрытом тесте — 0.8, разрыв устойчив и объясняется другим распределением запросов (подробнее — в разделе попыток).

### Подробности

1. Полнотекстовый поиск (Elasticsearch) BM25 между search_query и полями объявления с бустами: title x3, params_flat x1, description x2. Дополнительные бусты за совпадения по фильтрам: полное совпадение набора ключей param_keys (+4.0), совпадение значения конкретного ключа param_<slug> (+3.0), совпадение location_id (+8.0, только для не-доставки).

Жёсткие фильтры (must):

- рейтинг — если в запросе есть фильтр «Рейтинг пользователя N звёзд» (rating >= N);
- категория — если в запросе задана search_category;
- локация — если запрос не является запросом с Авито Доставкой: пользователь с доставкой изначально рассматривает варианты из других городов, отсекать их нельзя.

2. Dense-поиск (Qdrant) Эмбеддинг объявления: title + params_flat + description (полное описание — эксперимент с усечением до 200 символов поля desription снизил метрику с 0.84 до 0.78, откачен). Эмбеддинг запроса: search_query + search_infm_params_text. Фильтры: рейтинг, категория, локация (аналогично ES), поиск с limit=800.
3. Объединение RRF (k=30) по двум спискам, топ-50. Для запросов с «Сортировка для URL: дешевле/дороже» финальный топ-50 пересортировывается по цене.
4. Файнтюн энкодера MNRL, batch 256, 6 эпох со снижением lr (2e-5 → 5e-6), ресэмплинг одного позитива на запрос каждую эпоху. Раунд 2: hard negatives, намайненные моделью раунда 1 с теми же фильтрами, что и в проде (категория + локация) — 2 самых близких + 2 случайных из top-50, смешанные с обычными парами. Чекпоинт выбирался по dense Recall@50 на eval (эмбеддинги корпуса пересчитываются после каждого раунда).

### Что еще пробоавл (и почему отказался)

1. Гео-буст в ES. Буст объявлений в радиусе 50 км от центра локации запроса (центроиды по lat/lon). Дало +0.002 на eval, 0 на тесте — откачено. При этом ~15.5% позитивов теряются из-за жёсткого фильтра по location_id — проблема реальная, но гео-буст её не решает.
2. Классификатор microcat поверх энкодера (multi-task: contrastive + supervised). Идея из Query Understanding: предсказывать microcat запроса и бустить объявления из топ-3 категорий. Голова не обучилась при разумном lr, метрика не выросла — отказ. Ошибка, как выяснилось, сидит не в категоризации.
3. Двухпроходный Qdrant и взвешенный RRF — локальный rescue-проход и веса списков: −0.01 и +0.002 соответственно, импакта нет.
4. Кросс-энкодерный реранкер поверх union-пула вместо RRF. Модель обучена (pointwise BCE на том же rubert-tiny2), но в прод не пошла: по error analysis потенциал ограничен потерями «нашли, но не вошло в топ-50 RRF» (~5 п.п. на eval), а при последнем сабмите и устойчивом разрыве eval→тест риск невалидированного изменения показался выше ожидаемой выгоды. К тому же слишком долгий инференс на MPS (ускоритель MacBook).
