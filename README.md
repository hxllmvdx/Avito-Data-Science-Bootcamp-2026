### Запуск

Для того, чтобы запустить проект, у вас должен быть установлен и запущен `Docker`, а также обязательно пакетный менеджер `uv` (если его у вас нет, то вам сюда - [гайд по установке](https://docs.astral.sh/uv/getting-started/installation/)).

Первым делом поднимите `Docker`-контейнер проекта:

```bash
  docker compose up -d
```

Потом обязательно распакуйте веса:

```bash
  unzip finetuned_rubert.zip -d finetuned_rubert
```

Соберите Python-окружение:

```bash
  uv sync
```

Для того, чтобы запустить код выполните:

```bash
  uv run avito-data-science-bootcamp-2026
```

В папке data/ должны лежать train.parquet, benchmark_queries.parquet, benchmark_items.parquet. При первом запуске пересобираются кэши (data/items_parsed.parquet, data/item_embeddings.npy) и индексы ES/Qdrant — это долго (~10 минут), при последующих запусках используются кэши. Если меняется формат текста для эмбеддингов — кэши нужно удалить вручную. Кэш эмбеддингов запросов (data/query_embed_cache.npz) для пайплайна не нужен — он строится отдельным ноутбуком `analytics/3_build_query_embeddings.ipynb` и используется в экспериментах.

### Данные и признаки

**Запросы.** Для каждого поискового запроса используются `search_query` (текст), а также распарсенный `search_infm_params_text` — набор пар «ключ → значение» (вид услуги, тип услуги, место оказания, рейтинг пользователя, сортировка для URL и т.д.). Из параметров отдельно извлекаются `params_keys` (множество ключей) и `param_<slug>` (значения конкретных ключей) — они позволяют бустить объявления, у которых совпадает не только текст, но и структура услуги. Дополнительно используются `search_category`, `search_location_id` и `search_is_delivery_search`.

**Объявления.** Текст объявления для эмбеддинга собирается как `item_title_raw` + `params_flat` + `item_description_raw` (полное описание, без усечения). `params_flat` — это тот же формат «Ключ: значение», что и в `search_infm_params_text`, поэтому BM25 и dense-пространство видят согласованные тексты. Числовые признаки — `item_rating`, `item_price`; категориальные — `item_category_id`, `item_microcat_id`, `item_location_id`; координаты — `item_latitude`/`item_longitude` (для гео-анализа).

Такое представление выбрано потому, что запрос в этом домене почти всегда содержит не только свободный текст, но и структурированные фильтры, а объявление — длинное описание, в котором релевантность часто определяется именно совпадением параметров, а не общей семантикой.

### Архитектура

Весь код лежит в `src/avito_data_science_bootcamp_2026`:

1. `src/avito_data_science_bootcamp_2026/main.py` - точка входа: запуск всех стадий пайплайна
2. `src/avito_data_science_bootcamp_2026/parser.py` - парсинг `*_infm_params_text`, препроцессинг объявлений
3. `src/avito_data_science_bootcamp_2026/embeddings.py` - загрузка энкодера, API построения эмбеддингов
4. `src/avito_data_science_bootcamp_2026/qdrant_indexer.py` - индексация эмбеддингов в Qdrant
5. `src/avito_data_science_bootcamp_2026/es_indexer.py` - индексация объявлений в Elasticsearch
6. `src/avito_data_science_bootcamp_2026/searcher.py` - гибридный поиск (ES + Qdrant) и объединение через RRF

Также есть папка `analytics`:

1. `analytics/1_infm_params_aggregation.ipynb` - тут я начинал исследовать датасеты и потом написал код для извлечения параметров, также там описаны мои общие мысли и тд
2. `analytics/2_tune_rubert.ipynb` - файнтюн энкодера (контрастивное обучение).
3. `analytics/3_build_query_embeddings.ipynb` - построение кэша эмбеддингов запросов (`query_embed_cache.npz`), используется для ускорения экспериментов.
4. `analytics/4_error_analysis.py` - автономный error analysis: реконструирует детерминированный eval-срез, прогоняет поиск и классифицирует потери, а также сравнивает распределения benchmark и train. Использовался в какой-то момент для оценки решения и определения дальнейшей возможности роста.

### Модели и алгоритмы

Благодаря бэкграунду в поиске я сразу выбрал гибридную схему ретривала, которая оказалась верным фундаментом:

1. Elasticsearch (BM25) — полнотекстовый поиск;
2. Qdrant (dense) — семантический поиск по эмбеддингам;
3. RRF — объединение двух ранжированных списков в один.

Модель энкодера — cointegrated/rubert-tiny2: инференс должен работать на ноутбуке, а дообучение доступно в Colab/Kaggle. Для улучшения dense-поиска энкодер дообучен контрастивно (MNRL) на парах «запрос → кликнутое объявление» из train.parquet. Модель сходится быстро — заметный прирост качества наблюдается уже после первых эпох.

**Важно про пулинг.** Чекпоинт сохранён как `SentenceTransformer` с пулингом `cls` (`1_Pooling/config.json`), и именно CLS-векторами посчитаны эмбеддинги корпуса. Поэтому `TextEmbedder` теперь читает режим пулинга из конфига чекпоинта, а не хардкодит `mean`. Раньше запросы кодировались через mean, а объявления — через CLS, то есть query- и item-векторы лежали в разных пространствах (косинус между ними ≈ 0.5). Исправление вернуло ~+0.7 п.п. на гибриде.

**Полнотекстовый поиск (Elasticsearch).** BM25 между `search_query` и полями объявления с бустами: title x3, params_flat x1, description x2. Дополнительные бусты за совпадения по фильтрам: полное совпадение набора ключей `params_keys` (+4.0), совпадение значения конкретного ключа `param_<slug>` (+3.0), совпадение `location_id` (+8.0, только для не-доставки).

Жёсткие фильтры (must):

- рейтинг — если в запросе есть фильтр «Рейтинг пользователя N звёзд» (rating >= N);
- категория — если в запросе задана `search_category`.

Локация в ES — это **буст** (`should`), а не фильтр: жёсткое отсечение по городу делает только Qdrant.

**Dense-поиск (Qdrant).** Эмбеддинг объявления: title + params_flat + полное description. Эмбеддинг запроса: search_query + search_infm_params_text. Фильтры: рейтинг, категория, локация; поиск с `limit=800`.

Локация в Qdrant — жёсткий `must`, но применяется **условно**: если в локации запроса меньше 50 объявлений корпуса (в т.ч. 0), фильтр снимается, иначе запрос вообще не получил бы dense-кандидатов из своего города. При снятом фильтре вес Qdrant-канала в RRF понижается до 0.3. Параметры: `LOCATION_MODE="conditional"`, `LOCATION_POOL_THRESHOLD=50`, `LOCATION_QD_WEIGHT=0.3`.

**Объединение.** Взвешенный RRF (k=30) по двум спискам, топ-50. Бонус к RRF-скору за совпадение локации не используется (`LOCATION_BONUS=0`), так как обычный RRF учитывает только ранги, и бонус к сырому скору канала на порядок не влияет.

**Файнтюн энкодера.** MNRL, batch 256, 6 эпох со снижением lr (2e-5 → 5e-6), ресэмплинг одного позитива на запрос каждую эпоху. Раунд 2: hard negatives, намайненные моделью раунда 1 с теми же фильтрами, что и в проде (категория + локация) — 2 самых близких + 2 случайных из top-50, смешанные с обычными парами. Чекпоинт выбирался по dense Recall@50 на eval (эмбеддинги корпуса пересчитываются после каждого раунда).

### Проверка качества

**Протокол оценки.** Все замеры внутри проекта делались на фиксированной eval-выборке: 2000 уникальных запросов (seed=42), тексты которых исключены из обучения энкодера. Срез строится детерминированно — перед `.sample(seed=42)` выполняется сортировка по полям запроса, иначе порядок `group_by` в polars нестабилен между запусками и позиционные `query_id` указывают на разные запросы. Метаданные среза (поля запроса и позитивы) сохраняются в `output/train_eval_queries.parquet`, предсказания — в `output/train_predictions.csv`.

Метрика — Recall@50: доля кликнутых объявлений, попавших в топ-50 предсказаний, усреднённая по запросам. Дополнительно считаются срезы по размеру пула локации, наличию параметров и длине запроса.

Итог: на eval Recall@50 = **0.84**, на скрытом тесте (лидерборд) — **0.81**. Разрыв устойчив и объясняется другим распределением запросов (подробнее — в разделах «Анализ ошибок» и «Что еще пробовал»).

### Анализ ошибок

Для поиска точек роста написан `analytics/4_error_analysis.py`. Он реконструирует eval-срез, прогоняет поиск по уже поднятым ES/Qdrant и классифицирует каждый позитив (2211 позитивов, дедуп):

| Категория                                              | Кол-во | Доля   |
| ------------------------------------------------------ | ------ | ------ |
| found (в топ-50)                                       | 1852   | 83.76% |
| filtered_location (локация позитива ≠ локации запроса) | 250    | 11.31% |
| lost_in_rrf (был в пуле, не дошёл до топ-50)           | 107    | 4.84%  |
| not_found_anywhere                                     | 2      | 0.09%  |

Что выяснилось:

- **Локация — главный источник потерь.** Позитивов с `location_id != запроса` (не delivery) — 394 (17.82%). Из них Qdrant-канал не вернул **ни одного** (жёсткий must по локации), а ES-канал нашёл 323/394, потому что в ES локация — только буст. Это и привело к условному снятию must при малом пуле локации.
- **Резерв ранжирования.** Recall пула на глубине: 50 → 0.838, 100 → 0.884, 200 → 0.917, 400 → 0.943, 800 → 0.965. Разница recall(400) − recall(50) = **10.5 п.п.** — кандидаты в пуле есть, но RRF ставит в топ-50 не тех. Это зона для реранкера.
- **Сдвиг распределений benchmark vs train.** В benchmark заметно больше пустых `search_infm_params_text` (63.1% против 34.8%) и запросов с нулевым пулом локации (17.4% против 12.3%), тексты длиннее. Это объясняет, почему на тесте просадка: часть запросов попадает в срезы, где ретрив слабее.
- **Что сделано:** добавлено условное снятие must по локации (+0.26 п.п. на eval, +2.27 п.п. на срезе `loc_pool=0`), исправлен пулинг (CLS вместо mean), реранкер отклонён (см. ниже).

### Что еще пробовал (и почему отказался)

1. Гео-буст в ES. Буст объявлений в радиусе 50 км от центра локации запроса (центроиды по lat/lon). Дало +0.002 на eval, 0 на тесте — откачено. При этом ~15.5% позитивов теряются из-за жёсткого фильтра по location_id — проблема реальная, но гео-буст её не решает (в итоге решена условным снятием must).
2. Классификатор microcat поверх энкодера (multi-task: contrastive + supervised). Идея из Query Understanding: предсказывать microcat запроса и бустить объявления из топ-3 категорий. Голова не обучилась при разумном lr, метрика не выросла — отказ. Ошибка, как выяснилось, сидит не в категоризации.
3. Двухпроходный Qdrant и взвешенный RRF — локальный rescue-проход и веса списков: −0.01 и +0.002 соответственно, импакта нет.
4. LightGBM-реранкер (lambdarank) поверх union-пула ES+Qdrant. Попытка была: обучен на достижимых позитивах с признаками каналов (скоры, ранги, RRF, локация, microcat, цена). Значимого прироста не дал — дельта к RRF около +0.5 п.п., доверительный интервал включал 0, при этом реранкер менял топ-50 почти у всех запросов.
