### Запуск

Для того, чтобы запустить проект, у вас должен быть установлен и запущен `Docker`, а также обязательно пакетный менеджер `uv` (если его у вас нет, то вам сюда - [гайд по установке](https://docs.astral.sh/uv/getting-started/installation/)).

Первым делом поднимите `Docker`-контейнер проекта:

```bash
  docker compose up -d
```

Потом обязательно распакуйте веса:

```bash
  uzip finetuned_rubert.zip -d finetuned_rubert
```

Соберите Python-окружение:

```bash
  uv sync
```

Для того, чтобы запустить код выполните:

```bash
  uv run avito-data-science-bootcamp-2026
```

### Архитектура

Весь код лежит в `src/avito_data_science_bootcamp_2026`:

1. `src/avito_data_science_bootcamp_2026/__init__.py` - просто позволяет запускать проект bash-командой.
2. `src/avito_data_science_bootcamp_2026/main.py` - точка входа, содержит функцию с запуском всех стадий ретривала.
3. `src/avito_data_science_bootcamp_2026/parser.py` - парсит поля `*_infm_params_text` и препроцессит датасеты объявлений.
4. `src/avito_data_science_bootcamp_2026/embeddings.py` - грузит энкодер и дает API для построения эмбеддингов.
5. `src/avito_data_science_bootcamp_2026/qdrant_indexer.py` - тут объявления индексируются внутри Qdrant
6. `src/avito_data_science_bootcamp_2026/es_indexer.py` - аналогично `qdrant_indexer.py`, только для Elasticsearch
7. `src/avito_data_science_bootcamp_2026/searcher.py` - пайплайн гибридного поиска по Qdrant и ES с последующим объединением через RRF

Также есть папка `analytics`:

1. `analytics/1_infm_params_aggregation.ipynb` - тут я начинал исследовать датасеты и потом написал код для извлечения параметров, также там описаны мои общие мысли и тд
2. `analytics/2_tune_rubert.ipynb` - просто код для файнтюна энкодера.

### Общая идея решения

Как только я увидел описание ТЗ, сразу решил делать гибридный поиск, можно считать, что я считерил, поскольку мне повезло изначально знать, как примерно нужно строить _retrieval_. Выбрал `Elasticsearch` для полнотекстового поиска через базовый `BM25` и `Qdrant` для _dense_-поиска, вроде бы база для подобных задач. Также для улучшения качества _dense_-поиска я решил дообучить `cointegrated/rubert-tiny2`, выбрал именно эту модель, поскольку инференс надо было делать на личном ноутбуке, а для дообучения есть только `Google Colab`. После ретривала из обеих БД, делаю RRF. Все просто

### Подробности

1. **Полнотекстовый по ES:** считаем BM25 между `search_query` и полями `title`, `description` и `params_flat` (плоские распаршенные параметры) с соответствующими им бустами, потом за полное совпадение `param_keys` (ключей фильтров в запросе и объявлении, они тоже распаршены) и за совпадение каждого `param_<slug>` (типа _param_тип_услуги_) также бустим. Жестко фильтруем по рейтингу, если такой параметр есть, жестко фильтруем по категории поиска, если она есть и жестко фильтруем по совпадению локации запроса и объявлении (в одном из исследований обнаружил, что там огромная корреляция с кликом), если запрос не является с запросом с авито-доставкой (тут уже пользователь изначально рассматривает возможность заказать не из своей локации, нельзя отсекать).
2. **Dense в Qdrant:** аналогично фильтруем по рейтингу, категории и локации, склеиваем запрос с плоскими параметрами и ищем глубоко. В Qdrant хранятся эмбеддинги, построенные как title + params_flat + description объявления.

Очевидно надо было дообучить энкодер при помощи _contrastive-learning_. Для чего? Сближать похожие запросы и соответствующие им объявления в пространстве. Тут для меня удивительным было то, что даже небольшое количество данных (можно в ноутбуке глянуть, видно, что пар немного) хватило, чтобы увеличить метрику на 0.12, довольно много.

Все замеры, указанные тут делались на фиксированной выборке из 2к запросов.

### Что еще хотел сделать, но не получилось или не дало значимого результата

1. Пытался бустить запросы из соседних локаций, строя центроиды локаций по `lat` и `lon` объявлений. Потом бустил объявления, которые находились в радиусе 50km от точки запроса (точкой запроса считал центр `location_id`). Значимого прироста не дало, зато съело попытку сабмита, хотя по сути около 15% объявлений я терял как раз из-за жесткого фильтра по id локации.
2. Из-за моего бекграунда в _Query Understanding_-команде маркетплейса пришла идея о том, что можно было бы сделать классификатор `microcat_id`, получать топ-3 предсказаний и бустить объявления в соответствующих категориях. Тут я знаю много в целом, думал даже попытаться по item'ам восстановить таксономию и использовать эмбеддинг ее графа как фичу (см. статью Amazon - Hierarchical Query Classification, как-то так вроде), но после попытки обучить классификатор поверх моего энкодера (точнее сделать их общее обучение, сразу contrastive и supervised learninng) понял по метрике, что лучше не стоит тратить время, да и ошибка к тому же по большей части в других местах
3. Потом я придумывал всякие взвешенные _RRF_, двойной ретривал из векторной БД, но импакта это также не дало.
4. Самой последней и, вероятно, рабочей идеей, стало дообучение cross-encoder'а для "умного" RRF, я даже обучил модельку, но понял, что инференс слишком долгий будет и даже так, вряд ли он мне даст значимый прирост (я считаю около 5 процентов тех, что теряются именно из-за RRF) и решил не тратить время.
